This map records what existing assertions can protect during frontend migration and where additional evidence is
needed. Read it alongside the [behavior inventory](BEHAVIOR_INVENTORY.md) and [route inventory](ROUTE_INVENTORY.md).
The family prefixes below match the behavior inventory; a family reference does not mean every behavior in that
family has coverage. The original 2026-10-04 assessment reviewed tests as source, without a current application-suite
execution or coverage report. Its gaps remain a native starting-point inventory, not a current pilot certification;
later executed pilot and test-cost evidence belongs to the [paired review](PILOT_PARITY_REVIEW.md). The separate
[visual baseline](VISUAL_BASELINE.md) records one-off browser captures and the narrower
native overview-search check; those are not committed application-suite results.

The [second-pass edge-case records](EDGE_CASES.md) add concrete special-use and failure scenarios, with narrower
assertion evidence and open verification questions. Use those records when selecting checks for a migrated slice;
this family-level table alone is not a complete parity checklist.

## How to read the evidence

| Evidence label | Boundary actually exercised | Limit |
|---|---|---|
| Unit | Imported production calculations, normalization, formatting, policy, job logic or isolated tooling fixtures | Does not establish Surveyor route wiring, database transactions or browser behavior. |
| Frontend | Imported browser modules/components with restored stubs or happy-dom; production Pug/SSR rendering | Does not establish real layout, browser focus mechanics, Bootstrap integration or the live HTTP stack. |
| Client browser | A real browser exercising isolated client/template/built-entry fixtures in the frontend layer | Does not establish the live application, session store, database or full setup. A browser runner alone does not make this E2E. |
| Integration | Real TypeORM metadata and disposable MariaDB; selected controllers; genuine production server-component integration, or prepared source-development browser workflows | A database-free Express/Vite/SSR/HTTP fixture establishes its server-component boundary, not session/database/business workflow. Direct-controller fixtures do not establish Express/browser behavior; source-server journeys do not establish built-application delivery. |
| HTTP E2E | Requests through the built server and fully prepared database using Playwright `APIRequestContext` | A successful form POST or HTML string assertion is not a browser form interaction. |
| Browser E2E | A real Playwright page exercising a critical journey through the built application and full setup/database | Scope is the tested journey and configured browser, not all pages or all browsers. Isolated fixtures belong to the client layer. |

The [Testing Guide](../TESTING_GUIDE.md#vitest-configuration) owns current runner, coverage and CI details; use its
[staged amendments](staged/TESTING_GUIDE.md#risk-and-test-cost) for migration-specific risk selection. Executable
[Vitest](../../vitest.config.mts) and [Playwright](../../playwright.config.ts) configurations remain authoritative.
Coverage does not measure Pug/Sass layout. The managed E2E server starts the compiled application through
`e2e:init`; that is not a build step.

## Verification selection for subsequent migration slices

Follow the [Testing Guide](../TESTING_GUIDE.md) and [package scripts](../../package.json). Start with the cheapest
layer that protects the changed behavior. Existing backend algorithms and persistence tests should continue to
protect their contracts; a UI rewrite does not require duplicating all their cases in a browser.

For a migrated slice, select its frontend state/component cases first; run the existing integration cases when
controller, transaction or serialization behavior changes; keep one critical browser workflow for the actual
route/session/component boundary. When replacing a reload assertion, assert both confirmed data changes and retained
UI state. A new response envelope or versioned endpoint needs contract/route evidence even if its DBAL is unchanged.

Database-backed suites rebuild their selected schemas. Verify the effective disposable target and credentials before
running them; `npm test` includes integration tests, while `npm run test:quick` is database-free. No application test
execution is certified by this source map. Latest commands/results belong to the [paired review](PILOT_PARITY_REVIEW.md);
the [visual baseline](VISUAL_BASELINE.md) retains separate build/capture evidence.
Optional documentation reports remain advisory and are not application correctness tests or delivery prerequisites.
