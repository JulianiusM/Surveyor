This map records what existing assertions can protect during frontend migration and where additional evidence is
needed. Read it alongside the [behavior inventory](BEHAVIOR_INVENTORY.md) and [route inventory](ROUTE_INVENTORY.md).
The family prefixes below match the behavior inventory; a family reference does not mean every behavior in that
family has coverage. The original 2026-10-04 assessment reviewed tests as source, without a current application-suite
execution or coverage report. Its gaps remain a native starting-point inventory, not a current pilot certification;
later executed pilot and test-cost evidence belongs to the [paired review](PILOT_PARITY_REVIEW.md). The separate
[visual baseline](VISUAL_BASELINE.md) records one-off browser captures and the narrower
native overview-search check; those are not committed application-suite results.

The [second-pass edge-case records](EDGE_CASES.md) add concrete special-use and failure scenarios, with narrower
assertion evidence and open verification questions. Use those records when selecting checks for a migrated slice;
this family-level table alone is not a complete parity checklist.

## How to read the evidence

| Evidence label | Boundary actually exercised | Limit |
|---|---|---|
| Unit | Imported production calculations, normalization, formatting, policy, job logic or isolated tooling fixtures | Does not establish Surveyor route wiring, database transactions or browser behavior. |
| Frontend | Imported browser modules/components with restored stubs or happy-dom; production Pug/SSR rendering | Does not establish real layout, browser focus mechanics, Bootstrap integration or the live HTTP stack. |
| Integration | Real TypeORM metadata and disposable MariaDB; selected controllers invoked directly | Does not generally exercise Express middleware, cookies, HTML rendering or browser interaction. |
| HTTP E2E | Requests through the built server using Playwright `APIRequestContext` | A successful form POST or HTML string assertion is not a browser form interaction. |
| Browser E2E | A real Playwright page with controls, navigation and rendered-state assertions | Scope is the tested journey and configured browser, not all pages or all browsers. Some browser fixtures isolate templates rather than use live application data. |

The [Testing Guide](../TESTING_GUIDE.md#vitest-configuration) owns current runner, coverage and CI details; use its
[staged replacement](staged/TESTING_GUIDE.md#risk-and-test-cost) for migration-specific risk selection. Executable
[Vitest](../../vitest.config.mts) and [Playwright](../../playwright.config.ts) configurations remain authoritative.
Coverage does not measure Pug/Sass layout. The managed E2E server starts the compiled application through
`e2e:init`; that is not a build step.

## Refresh and multi-client gaps to close during implementation

The migration introduces a persistent client lifecycle. Existing stale-response tests and database races are useful
starting points for **REF-01–REF-06**, but do not establish the behavior of a new router, query cache or edit-conflict
interface.

| Risk | Existing evidence to retain | Focused future acceptance scenario and layer |
|---|---|---|
| Periodic refresh while a form is dirty | Overview/select stale-response suppression; retained denied property drafts | **Frontend:** refresh clean display fields while preserving draft values, focus and selection; retain the original edit revision. Show changed/deleted remote state without silently overwriting the draft. |
| Two users edit the same ordinary record | Relationship and invoice revisions; linked-plan conflict tokens | **Integration:** conditional write rejects an old revision atomically. **Browser:** two contexts open the same record, one saves, the other sees a conflict, reviews current values and deliberately retries. Do not infer this contract already exists for every entity. |
| Capacity contention | Sequential packing/drivers hard-cap cases with item locks; activity sibling-plan concurrency. Event registration checks capacity before its write transaction (IMP-037), so it has a source-level protection gap as well as missing concurrency evidence. | **Integration:** two concurrent final-place writes for event registration, packing, drivers and applicable activity caps. Assert accepted count and persisted assignments, not only error text. **Browser:** verify one representative rejected request updates the displayed capacity and preserves unrelated draft state. |
| Failed refresh / offline / recovery | `retains the current surface on errors and retries the failed navigation` in overview frontend; event-picker retry cases | **Frontend:** failed read leaves last confirmed data visibly stale, clears pending indicators, respects backoff, and can retry; reconnect/focus refresh does not duplicate timers. Cover cancellation and out-of-order responses on route change. No reviewed suite proves app-wide background refresh today. |
| Stale invoice calculation after another client pays or edits | Integration rejects old preview revisions and keeps paid state/share IDs | **Browser:** hold an open preview, change server data from another context, reject the old apply, retain saved financial values and require another review. |
| Uncertain upload or mutation result | Invoice frontend distinguishes definite rejection from unconfirmed outcome; organizer browser E2E already drops a real committed response and verifies one saved invoice after recovery | **Frontend:** mutation-success followed by read failure must remain a confirmed mutation with stale display, not invite another submission. **Browser:** retain organizer response-loss recovery and cover the participant-upload variant without duplicate invoices. Server idempotency, if introduced, requires its own integration check. |
| Profile switch, logout or revocation while reads are pending | Backend profile/privacy assertions; HTML-login responses preserve permission/archive drafts | **Frontend:** identity-scoped keys, cancellation and cache clearing reject late old-profile responses. **Browser:** switch profile or expire/revoke a session with private content open and confirm the new context cannot see/reuse the old data or submit its commands. |
| Route lifecycle leaks and stale notifications | Overview disposal/cancellation cases; alert timer cleanup | **Frontend:** route leave releases observers/timers/listeners; remount creates one subscription; a late mutation result cannot update an unrelated page. **Browser:** Back/Forward/direct URL/hash/scroll continuity for the first migrated slice. |
| Shared localization and API contracts | Existing date-format, payload and response checks are feature-specific | **Unit/type checks:** one contract source produces usable client/server shapes; invalid wire data is rejected at the boundary; locale catalogs have complete keys/placeholders and the same backend/frontend messages. **Frontend:** switching language updates controls and errors without changing machine values. **Browser:** one representative validation error in each supported pilot language. These checks require the new contract/catalog implementation and are not present migration evidence. |

## Verification selection for subsequent migration slices

Follow the [Testing Guide](../TESTING_GUIDE.md) and [package scripts](../../package.json). Start with the cheapest
layer that protects the changed behavior. Existing backend algorithms and persistence tests should continue to
protect their contracts; a UI rewrite does not require duplicating all their cases in a browser.

For a migrated slice, select its frontend state/component cases first; run the existing integration cases when
controller, transaction or serialization behavior changes; keep one critical browser workflow for the actual
route/session/component boundary. When replacing a reload assertion, assert both confirmed data changes and retained
UI state. A new response envelope or versioned endpoint needs contract/route evidence even if its DBAL is unchanged.

Database-backed suites rebuild their selected schemas. Verify the effective disposable target and credentials before
running them; `npm test` includes integration tests, while `npm run test:quick` is database-free. No application test
suite was executed for this map. Separate build/capture verification belongs to the [visual baseline](VISUAL_BASELINE.md).
Optional documentation reports remain advisory and are not application correctness tests or delivery prerequisites.
