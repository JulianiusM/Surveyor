These cases extend the [behavior inventory](BEHAVIOR_INVENTORY.md), particularly SRV, EVT, PCK, DRV and ACT.
They identify details that a common component or shared request layer could accidentally erase. IDs are stable
acceptance references, not a claim that migration or testing is complete. The [test coverage map](TEST_COVERAGE.md)
owns overall coverage assessment; the [route inventory](ROUTE_INVENTORY.md) owns HTTP methods and authorization entry points.

An **assertion** below means an assertion inspected in existing test source. A **gap** means the listed test or source
does not establish that case; no application tests or browser interactions were executed for this second pass.
The [remediation register](../backlog/documentation-remediation.yml) owns transient defects. Its existing IMP references are
cross-references, not instructions to preserve a defect as a feature. Source-level uncertainties remain review cases.

## Identity and assignment accounting

| ID and trigger | Invariant to retain | Implementation and assertion/gap evidence |
|---|---|---|
| **EC-PART-001** — A full account switches its active profile, or a guest participates. | Ballots, attendance and item commitments belong to the active **profile ID**. Do not merge family profiles into one account participant or key them by display name. | [Survey submission](../../src/controller/surveyController.ts), [event registration](../../src/controller/eventController.ts), [packing assignment](../../src/controller/packingController.ts) and [driver assignment](../../src/controller/driversController.ts) consume profile identity. [Survey tests](../../tests/integration/survey-workflows.spec.ts), `keeps one participant ballot isolated from another`, assert separate stored answers. Gap: these tests do not prove a live SPA cache is cleared during an active-profile switch. |
| **EC-PART-002** — The same profile takes several packing items or several rides. | A row's assignment count counts its commitments; list **Participants** deduplicates assigned profiles across rows. Packing excludes Everyone rows from participant, open and empty counters. Driver identity does not itself count as a passenger. | Both controllers' `fetchForView` aggregate assignee profile IDs; [driver count decision](../decisions/DEC-003-DRIVER-LIST-PARTICIPANT-COUNT.md) establishes the deliberate driver/passenger distinction. [Native controller counters](../../tests/integration/controller-smoke-workflows.spec.ts), [packing Everyone/count assertions](../../tests/integration/packing-api.spec.ts) and [driver workflows](../../tests/integration/drivers-workflows.spec.ts) protect their distinct persisted/view-model counts; these alone are not complete rendered-counter matrices. |
| **EC-PART-003** — A retry arrives for an already-held packing item or passenger place when the row is full. | An existing assignment succeeds idempotently before the hard-cap check; a genuinely new assignment at capacity fails with 409. A missing row is 404. Do not count a successful retry as a new place. | `assignItem` in [packing](../../src/controller/packingController.ts) and [drivers](../../src/controller/driversController.ts); [packing](../../src/modules/database/services/PackingService.ts) and [driver](../../src/modules/database/services/DriverService.ts) DBAL lock the item and read existing assignment/count in one READ COMMITTED transaction. [Native Packing controller assertions](../../tests/integration/controller-smoke-workflows.spec.ts) retain idempotence/sequential rejection; [v1 Packing assertions](../../tests/integration/packing-api.spec.ts) race two actors and require one success, one 409 and one persisted assignment. The driver final-place race remains a separate unproven boundary. |
| **EC-PART-004** — Another client fills or deletes a row after it was rendered. | Server capacity/identity results remain authoritative. A count cached before submission cannot authorize an assignment, and optimistic increments must not survive a rejected mutation. | [Assignment browser helper](../../src/public/js/shared/entity-assign.ts) currently updates local controls then schedules a reload after success. EC-PART-003 establishes the server lock. Gap: no reviewed packing/driver browser test covers a stale rendered row and a concurrently rejected assignment. |
| **EC-PART-005** — A packing item changes to Everyone, or the user checks Packed. | Everyone is a shared requirement; Packed is a browser-local checklist. Its storage key is list ID plus item ID, **not profile ID**. A checked row becomes green; unchecking an Everyone row restores blue. This does not change server assignments or other browsers. | [Packing browser module](../../src/public/js/packing.ts), `initPackedToggle` and `reorderRequiredRows`; [packing view](../../src/views/packing/packing-view.pug). Gap: reviewed workflow tests cover the persisted Everyone flag, not storage restoration or profile-switch behavior. IMP-024 owns hidden individual assignments on Everyone rows. |
| **EC-PART-006** — A manager reduces a row's maximum or toggles Everyone while assignments exist. | Existing assignments are business records, not disposable row presentation. Migration must explicitly reconcile displayed occupancy and eligibility; it must not silently delete commitments to make a new maximum appear valid. | [Packing attribute updates](../../src/controller/packingController.ts), [driver attribute updates](../../src/controller/driversController.ts), and the respective DBAL update functions persist metadata without removing assignments. Existing IMP-025 and IMP-026 own capacity-validation discrepancies; IMP-024 owns Everyone assignment behavior. Gap: no reviewed test establishes a safe concurrent capacity-edit/assignment result. |
| **EC-PART-007** — Someone creates a ride or takes several rides. | The creating profile supplies the driver identity. Passenger capacity excludes the driver; creating an offer does not insert a passenger assignment. Multiple offers and multiple passenger commitments are distinct records. | [Driver controller](../../src/controller/driversController.ts), `quickAddItem`; [DriverService](../../src/modules/database/services/DriverService.ts), creation versus assignment functions; [driver workflows](../../tests/integration/drivers-workflows.spec.ts) assert driver-authored journeys and passenger assignments separately. IMP-027 owns the current participation-discovery discrepancy; do not infer discovery membership from the Participants counter. |

## Surveys: recurring choices and replacement ballots

| ID and trigger | Invariant to retain | Implementation and assertion/gap evidence |
|---|---|---|
| **EC-PART-008** — A survey asks for the last Monday of the month. | A choice is weekday plus occurrence `1`, `2`, `3`, `4` or `LAST`. `LAST` means fourth or fifth occurrence depending on the month. It is not a fifth-only choice or a particular calendar date, month, year or time. | [Creation browser module](../../src/public/js/survey-create.ts), [voting template](../../src/views/surveyor/survey-vote.pug), [survey controller](../../src/controller/surveyController.ts). Gap: creation/order tests do not exercise calendar interpretation; preserve the machine value `LAST` when translating labels. |
| **EC-PART-009** — A participant selects Maybe, leaves a choice unchanged, or sees a newly added choice. | `yes`, `maybe` and `no` are separate stored answers. An explicitly submitted empty value saves as `no`; the form defaults an unanswered choice to No, while the results can still distinguish absence of a stored response. Do not convert Maybe to a boolean. | [Voting template](../../src/views/surveyor/survey-vote.pug), [SurveyService](../../src/modules/database/services/SurveyService.ts), `saveResponse`; [survey workflows](../../tests/integration/survey-workflows.spec.ts) explicitly assert Maybe and empty-to-No persistence. Gap: rendered no-response/new-choice states are not asserted there. |
| **EC-PART-010** — A participant resubmits a subset of choices, or forges a choice ID from another survey. | Validate the complete submitted ballot before deleting the old ballot. Only this survey's combination IDs and supported answer values are accepted. Successful submission replaces this profile's answers in this survey, without affecting another profile. | [Survey controller](../../src/controller/surveyController.ts), `submitResponses`; [survey workflows](../../tests/integration/survey-workflows.spec.ts) assert foreign-choice rejection and profile isolation. The replacement test manually calls the deletion service before submission; it does **not** establish concurrent or atomic HTTP ballot replacement. Controller deletion and per-answer saves are separate awaits: lost response/parallel submission remains an explicit gap. |
| **EC-PART-011** — A guest or ordinary participant adds a combination. | Admitted participants can add choices; this is not an owner-only action. Survey ownership still controls owner property changes. A generic ACL component must not introduce co-admin or Group Permissions controls. | [DEC-001](../decisions/DEC-001-SURVEY-COMBINATION-AUTHORIZATION.md), [DEC-005](../decisions/DEC-005-SURVEY-CREATION-PERMISSIONS.md), [survey routes](../../src/routes/survey.ts), [survey controller](../../src/controller/surveyController.ts). [Entity property tests](../../tests/integration/entity-properties.spec.ts), `keeps survey property writes owner-only despite general permission rows`, assert the separate ownership rule. Gap: add-combination authorization is primarily route/decision evidence. |
| **EC-PART-012** — A survey is opened from an event-related URL or duplicated. | Surveys retain their standalone recurring-scheduling model. Do not interpret incidental query parameters as a persisted event relationship. Duplication must preserve supported description/choice data while creating a distinct survey. | [Survey creation](../../src/controller/surveyController.ts) does not pass an event relationship to persistence. DEC-005 and IMP-021 record the deliberate standalone boundary versus leftover routing. IMP-020 owns duplication prefill errors. The [core E2E](../../tests/e2e/core-workflows.spec.ts) query-parameter smoke does not assert a saved event relationship. |
| **EC-PART-013** — A participant answers only No or later changes all answers. | Any stored response establishes survey participation for overview discovery; participation is not restricted to Yes. Named results remain visible according to this survey's existing admission model. | [SurveyService](../../src/modules/database/services/SurveyService.ts), `getSurveyParticipationQuery`; [survey workflows](../../tests/integration/survey-workflows.spec.ts), `lists surveys answered by a participant`, tests discovery after an answer but not a No-only ballot. Gap: explicit No-only overview regression. |

## Event attendance, dates, deadlines and diet

| ID and trigger | Invariant to retain | Implementation and assertion/gap evidence |
|---|---|---|
| **EC-PART-014** — A participant chooses a single-day stay or updates dates. | Arrival and departure are inclusive calendar dates within the event window; arrival must not follow departure. Keep date-only fields separate from zoned deadline instants. | [Event controller](../../src/controller/eventController.ts), `registerAttendance` and `updateRegistrationDates`; [date utility](../../src/modules/lib/util.ts), `isWithinWindow`. [Application utility tests](../../tests/unit/application-utilities.spec.ts) assert inclusive totals, zero-count days and clamping. Gap: registration uses a shape regex plus lexical bounds, not the stronger calendar validator used by event property edits; invalid real-calendar dates need boundary review. |
| **EC-PART-015** — An organizer edits only the event title or changes the deadline's time zone. | Omitted deadline/date fields retain their saved values. An explicitly supplied local deadline is interpreted in the supplied zone, then current zone, then UTC. A title-only save must not shift an instant or clear post-deadline flags. | [Event controller](../../src/controller/eventController.ts), `updateEventSettings`; [entity property tests](../../tests/integration/entity-properties.spec.ts), `keeps dates and zoned deadline untouched on title-only saves and rejects invalid combined dates atomically`. [Deadline display](../../src/public/js/events.ts), `deadlineUpdater`, shows local and configured-zone representations. Gap: no reviewed browser test covers DST overlap/gap input and display together. |
| **EC-PART-016** — Capacity becomes full while an already registered participant edits their stay. | Capacity prevents new registrations, not updates of an existing one. Null/omitted capacity means unlimited; persisted zero is meaningful. Do not infer that an event owner's access privilege creates an attendance row. | [Event controller](../../src/controller/eventController.ts), `registerAttendance` and `isEventFull`; [EventService](../../src/modules/database/services/EventService.ts), `register` and `isRegisteredForEvent`. [Event workflows](../../tests/integration/event-workflows.spec.ts) separately assert update without duplication, unlimited/full queries, and owner access. Gap: update-at-full and persisted-zero boundaries are not directly covered by those cases. |
| **EC-PART-017** — Two new profiles race for the final event place. | The migration acceptance case must assert the persisted registration count and each response, not only a preflight Full indicator. | [Event controller](../../src/controller/eventController.ts) checks fullness before `withEventTransaction`; [EventService.register](../../src/modules/database/services/EventService.ts) does not repeat that policy under an event capacity lock. The [event workflow](../../tests/integration/event-workflows.spec.ts) full test is sequential and queries fullness after one registration. IMP-037 owns this capacity-check/write gap; no concurrent reproduction is claimed. This differs from the locked packing/driver assignment path in EC-PART-003. |
| **EC-PART-018** — An existing participant changes dates, diet or cancellation after the deadline. | These are three independent settings. Date changes compare submitted dates; diet changes compare selections and notes; cancellation has its own check. A permitted category must not silently enable another category. | [Event controller](../../src/controller/eventController.ts), `registerAttendance`, `isDietaryEqual`, `cancelRegistration`; [entity property tests](../../tests/integration/entity-properties.spec.ts) assert canonical flag permissions. Gap: stored absent notes versus submitted empty strings need a no-op diet regression; configuration tests alone do not prove unchanged registration submission succeeds. IMP-038 owns that equivalence defect; IMP-009 owns the recorded permission-name discrepancy. |
| **EC-PART-019** — A participant combines dietary choices or submits optional notes. | No dietary choices is accepted. Any nonempty selection needs a meal preference. Vegetarian and Vegan exclude each other and meat/fish; Meat and Fish may coexist. Allergies and Comment require their respective additional information. Persistence deduplicates selected choices and replaces the previous set. | [Event controller](../../src/controller/eventController.ts), `checkMeals`; [EventService](../../src/modules/database/services/EventService.ts), `replaceDietaryChoicesTx`. [Event workflows](../../tests/integration/event-workflows.spec.ts) assert unique dietary rows/notes and replacement. Gap: whitespace-only notes, all incompatible combinations and after-deadline equivalence are not established by those persistence assertions. |
| **EC-PART-020** — Two late registrants use the final permitted use of one registration link. | Token status is event-scoped and checks revocation, expiry and usage. Eligibility preview is rechecked under the token row lock; consumption and attendance commit together, so a failed attendance write cannot spend the token. A token bypasses deadline eligibility, not capacity or date/diet validation. | [Event controller](../../src/controller/eventController.ts), `bypassStatus`, `canBypassDeadlineWithToken`, `registerAttendance`; [EventService](../../src/modules/database/services/EventService.ts), token lock/consumption. [Event workflows](../../tests/integration/event-workflows.spec.ts), `creates, validates, consumes, and reports a bypass link`, uses the real controller transaction. Gap: no reviewed test races final use or asserts rollback after a failed attendance write. |
| **EC-PART-021** — An organizer creates/copies a late-registration link, or its recipient must first become a guest. | The copied URL must identify the newly created token; copying an existing row must identify that row's token. The token must survive the recipient's authorized onboarding journey. These are separate flows from token consumption. | [Registration-link browser module](../../src/public/js/modules/reg-links.ts), [event API](../../src/routes/api/event.ts), [guest flow](../../src/middleware/guestFlowFactory.ts). IMP-007 owns submitted Uses handling; IMP-010 owns onboarding token loss; IMP-035 owns fresh-link auto-copy response handling. Fresh-link auto-copy and existing-row Copy need separate browser assertions; the token service test in EC-PART-020 proves neither clipboard path. |
| **EC-PART-022** — An organizer edits/deletes registration ID N through a different event. | The event ID scopes the write as well as the read. Organizer date edits require Manage Registrations and still satisfy the event date window. | [Event controller](../../src/controller/eventController.ts), `updateRegistrationDates`; [EventService](../../src/modules/database/services/EventService.ts), `updateRegistrationDates` and `deleteRegistration`; [event API](../../src/routes/api/event.ts). [Event workflows](../../tests/integration/event-workflows.spec.ts) assert successful correctly scoped updates/deletes. Their titles alone do not establish a forged-parent rejection assertion. |

## Activity requirements and availability

| ID and trigger | Invariant to retain | Implementation and assertion/gap evidence |
|---|---|---|
| **EC-PART-023** — A profile visits a linked plan without an attendance row, or loses registration after taking a slot. | Page access and assignment eligibility are separate. Self-assignment requires registration unless external assignees are enabled. Existing commitments remain removable even after eligibility changes. A profile name remains available for an existing external assignee. | [Activity controller](../../src/controller/activityController.ts), `authorizeSelfAssignment`; [activity workflows](../../tests/integration/activity-workflows.spec.ts) assert external profile names, default registration rejection and enabled external assignment. Gap: post-registration-removal unassignment is source-established, not directly asserted by those tests. |
| **EC-PART-024** — A nonregistered profile is included in recommendation candidates. | Enabling external assignees does not authorize arbitrary profile IDs in a recommendation payload. Current event registrations plus permitted existing external assignments define eligible recommendation participants. A preserved override is not authorization. | [Activity controller](../../src/controller/activityController.ts), `buildPlanRecommendationContext`, `applyActivityRecommendationOperations`; [activity property integrity tests](../../tests/integration/activity-property-integrity.spec.ts) assert that old-event profiles are excluded, retained work is warned/rejected, and enabling external policy re-admits an already assigned profile. |
| **EC-PART-025** — A plan switches Free/Required or changes its date span. | Free mode does not allocate required shifts. Required mode needs exactly one saved nonnegative integer requirement for every stay length from one through the inclusive plan duration. Runtime calculation must not silently invent a missing saved duration. | [Activity controller](../../src/controller/activityController.ts), `updateRequirements`; [requirements engine](../../src/modules/activity/requirements.ts). [Activity workflows](../../tests/integration/activity-workflows.spec.ts) reject incomplete tables and Free auto-generation; [requirements unit tests](../../tests/unit/activity-requirements.spec.ts) assert saved values and missing-duration behavior. |
| **EC-PART-026** — A participant has a short stay, several roles, a personal override or a zero target. | Clamp attendance to the plan first; an empty intersection contributes zero. Matching role-scoped personal overrides take precedence, choosing their minimum; then personal-wide override, then minimum matching role requirement, then saved stay requirement. Role/personal values are complete targets, not added shifts or attendance-scaled values. Zero must not fall through. | [Requirements engine](../../src/modules/activity/requirements.ts); [requirements unit tests](../../tests/unit/activity-requirements.spec.ts) assert zero, precedence, exact role values and clamped stay summaries. [Frontend coverage tests](../../tests/frontend/activity-requirement-coverage.spec.ts) assert unsaved participant/role/stay values and zero survive live preview. |
| **EC-PART-027** — An organizer estimates a baseline or inspects coverage before saving. | Default stay values follow configured rounding; None follows the engine's upward integer result. Saved manual stay values remain authoritative. Total capacity/demand coverage and hypothetical open-role matching are estimates, not proof that each actual participant can fill each time slot or that a role was assigned. | [Requirements engine](../../src/modules/activity/requirements.ts), `applyRounding` and baseline/role matching; [requirements unit tests](../../tests/unit/activity-requirements.spec.ts) assert integer gaps, fixed demand, global role matching and exclusion of personally overridden participants. [Frontend coverage tests](../../tests/frontend/activity-requirement-coverage.spec.ts) distinguish hard capacity from allowed-overfill minimum and recompute unsaved drafts. |
| **EC-PART-028** — Arrival and departure fall on a slot day. | Before arrival/after departure is outside attendance. Arrival mornings are ineligible; arrival slots starting at/after 12:00 require the arrival-evening setting. Departure slots before 12:00 require the departure-morning setting; later slots are ineligible. With missing times, explicit boundary hints are used. Same-day arrival/departure must undergo both checks. | [Availability engine](../../src/modules/activity/availability.ts), `collectAssignmentWarnings`; [auto-assignment unit tests](../../tests/unit/activity-auto-assignment.spec.ts), `uses only allowed arrival and departure boundary slots`, asserts boundary allocation. Gap: a dedicated same-day stay/missing-time browser warning matrix was not established. |
| **EC-PART-029** — Slots touch at 10:00, occur on different dates or have incomplete times. | Only strict time overlap on the same day counts. Ending exactly when the next begins is allowed; incomplete timeboxes do not establish overlap. Sorting prioritizes day, then defined start times, then position. Do not replace these rules with an all-day conflict assumption. | [Timebox engine](../../src/modules/activity/timebox.ts); [linked recommendation unit tests](../../tests/unit/activity-linked-recommendations.spec.ts), parameterized `preserves the established touching/day/incomplete-timebox rules`, asserts these boundaries. [Activity workflows](../../tests/integration/activity-workflows.spec.ts) assert daily ordering. |
| **EC-PART-030** — A participant takes a full slot or named role. | Ordinary slot capacity and per-role capacity are distinct. Existing membership does not consume a second slot place when adding a role. Allowed slot overfill does not automatically lift a named role's positive maximum. Cross-plan slot IDs and unconfigured role names must be rejected. | [Activity controller](../../src/controller/activityController.ts), `authorizeSelfAssignment` and assignment-role methods; [activity workflows](../../tests/integration/activity-workflows.spec.ts) assert wrong-plan/role rejection, hard cap, idempotence and warning before permitted overfill. Gap: a simultaneous same-slot final-place/named-role race is not established by the sibling-plan race test. |

| ID and trigger | Invariant to retain | Implementation and assertion/gap evidence |

reads, local Packed restoration, ballot replacement under failure/contention, actual calendar validation at attendance

has a retained production-API integration case. Use the [current coverage map](TEST_COVERAGE.md) for retained and future
boundaries, and the [paired review](PILOT_PARITY_REVIEW.md) for actual execution, resolutions and limits. Source presence
alone does not establish a passed scenario or complete migration of the other features.

the replacement component boundary for preserved drafts, confirmation cancellation and refreshed server results,
without treating the former full reload as the required outcome. Shared date, identity, count and response components
